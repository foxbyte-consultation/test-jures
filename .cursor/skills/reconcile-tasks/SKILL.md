# reconcile-tasks

入り口は1つ。種別を決めたあと、既存タスクのタイトルと照合し、無いものだけを起票する。実装の掘り下げは詳細設計に残す。

## リソース

- 種別ごとの集め方と、タスクの書き方 → [reference.md](reference.md)

## 本線 — 足りないものを起票する

発言がバグでも追加の指示でもなければ、これで進める。

1. **必要なら要件定義を拾う** — ローカルの `{project}/要件定義.md` があるときは、機能名と優先度だけ読む。候補に残った行だけ概要を読む。ローカルが無いときだけ、そのプロジェクトの Notion 要件ページの見出しを取る。将来の行は起票しない。
2. **リポジトリから、これから作るべき内容を考える** — ルート、ページパス、エンティティ名だけを見る。ファイル本文は開かない。要件にあって、この面に無いものが、これから作るものである。要件に無い雛形（サンプルの記事・ユーザー管理など）は、作ってあるものに数えない。
3. **1〜2人日に割ってから起票する** — バイブコーディングで進む速さで見て、1タスクが1〜2人日を超えそうなら分割する。割り方は、その機能のDB設計、API 1本、利用者の操作1つのUI。既存タスクは対象案件のタイトルだけと照合し、同じタイトルが無ければ確認を待たずに軽量タスクを `{project}/wbs/` へ書く。Notion へは下の「Notionの起票先」に従って行を足す。ページ本文は作らない。依存は、それが終わるまで着手できないものだけにする。モックで進むUIは、APIの完了を待たせない。

## Notionの起票先

見るタスクDBは1つだけにする。HOME →「DB管理」の共通タスクDB、データソース「タスクDB」。案件ごとのタスクDBや、案件ページ内のインラインDBは見ない。ぽちもの「案件-ぽちも タスク一覧」内にあるインライン「タスクDB」は運用ミスでできた別データベースなので、照合にも起票にも使わない。

起票は共通タスクDBの「タスクDB」に行を追加し、プロジェクト名のリレーションで案件につなぐ。同じデータベースに後から足された空の「New data source」も派生なので使わない。タイトル照合は、このデータソースを対象案件のリレーションで絞った行だけ。URLと data_source_id は `product-management-skills` の `docs/notion_links.md`「共通（タスクの正本）」。足すプロパティはタイトル、ステータス、プロジェクト名まで。ページ本文は作らない。

## ほかのパターン

### バグ — 現内容から類推して起票する

見ている画面、差分、または指摘された操作から、期待と実際の差を類推する。リポジトリ全体の本文は走査しない。既存タイトルと重ならなければ、バグタスクを建てる。面があることは、バグを起票しない理由にしない。

### 追加要件 — 指示から類推して起票する

指示の文から、誰が何をできるようになりたいかを類推する。要件定義の機能名の言い換えなら本線に戻す。既存タイトルと重ならなければ、追加要件タスクを建てる。コード全体は見ない。

## 注意

- 対象は1案件に絞る。見るのは共通タスクDBのデータソース「タスクDB」のうち、その案件のリレーションが付いた行だけ。案件ページ内のタスクDB、空の「New data source」、他案件の行や親ページは開かない
- Notion の応答 JSON は会話に載せない。タイトルの文字列だけに落として照合する
- ページ本文を開くのは、その1件の詳細設計を始めるときと、タイトルが突合できないときだけ
- 起票したものは、作ったファイルパスとタイトルを結果として返す

## 実装リポジトリに置いたとき

正本は `product-management-skills` の `.claude/skills/reconcile-tasks/` である。各実装リポジトリの `.cursor/skills/reconcile-tasks/` は同じ手順を置く。

- コードの面は、いま開いているリポジトリ
- 要件とタスクの書き先は、隣接する `product-management-skills/{project}/`
- `NOTION_API_KEY` は、このリポジトリに `.env` が無ければ `product-management-skills/.env` を使う。キーは複製しない
