# reconcile-tasks — 入り口は共通、出口だけ分ける

## 共通

どの種別でも同じことをする。

- 既存タスクはタイトルだけ見て、同じなら作らない。Notion の応答 JSON は会話に載せない。呼び出した側でタイトルの文字列だけに落とし、その一覧だけを照合に使う
- タスクに残すのは、誰が、何をできて、何をもって完了か。詳細設計がそれを掘る
- 同じタイトルが無ければ起票する。事前の承認は待たない
- Notion に書くときはタイトルとプロパティだけ。ページ本文は作らない。キーは `product-management-skills/.env` の `NOTION_API_KEY`（実装リポジトリへは複製しない）。対象プロジェクトのデータベースに絞ってタイトル一覧を取る。本文を開くのは、その1件の詳細設計を始めるときと、タイトルが既存タスクと突合できないときだけ

## 種別ごとに集めるもの

| 種別 | 集めるもの | 集めないもの |
|------|------------|--------------|
| 穴埋め | 機能名、優先度、候補行の概要、ルート・ページパス・エンティティ名、既存タイトル | 要件定義の背景・技術スタック、ハンドラ本文 |
| 追加要件 | 指示の文、機能名の一覧、既存タイトル | コード全体、要件の本文 |
| バグ | 指摘された画面・操作、期待と実際の差、既存タイトル | 原因調査、リポジトリ全体のルート一覧 |

ローカルの `要件定義.md` があるときは、Notion の要件ページは開かない。Notion しか無いときは見出しブロックだけ取る。

穴埋めでコードの面を数えるとき、要件に無い雛形（`articles`、サンプルの `admin` や `users`）はどの機能も満たさない。`/auth` だけではオーナー認証を満たしたことにしない。パスがあることは、その機能が動くことではない。

## 大きさ

1タスクは1〜2人日。見積もりはバイブコーディングで実装する速さにする。ボタンの色や関数1つの分割までは割らない。

1〜2人日を超えそうなら、次の単位で別タスクにする。

- その機能のDB設計
- API 1本（1リソースの1操作）
- 利用者の操作1つ分のUI

依存に書いてよいのは、それが終わらないと着手できないものだけである。モックで組めるUIはAPIタスクに依存させない。APIは、そのAPIが読むテーブルのDB設計タスクにだけ依存してよい。同じ機能の横のAPIや、別の人のUIは依存に書かない。並列に着手できることを優先する。

## タスクに書くこと

```markdown
# {タイトル}

## 種別
穴埋め / 追加要件 / バグ

## ゴール
{誰が、何をできる状態か。バグは、直ったあとどの操作が期待どおりになるか。1〜2文}

## 要件
{観察できる振る舞い。成功したとき何が見えるか、失敗したとき何が起きるか。出典が要件の1行ならその範囲で書く。会話で言えていない分岐は TBD}

## 受け入れ条件
- [ ] {Yes / No で判定できること}
- [ ] {同上。2〜3個}

## 含めないこと
レイヤー配置、ファイルパス、実装手順、バリデーションの書き方。これらは詳細設計で掘る。

## 出典
{要件定義の番号、または指摘の一文}

## 依存
{ファイル名で分かるタスク。無ければ「なし」}
```

タイトルは種別が分かる名前にする。バグは画面と症状、追加要件は欲しい機能、穴埋めは要件の機能名。

受け入れ条件に、hook、ログ、API の呼び方は書かない。それは詳細設計の方針である。
